# Backend RD Mídia Indoor — Guia da fundação (para quem implementa módulos)

> Origem: AÇÃO 002 (marco M1 do agente W1, 2026-10-07). Contrato de API: `docs/contracts/API_CONVENCOES_AUTH_RBAC_REALTIME_v1.md`. Protocolo do player: `protocol/RD_PLAYER_PROTOCOL_v1.md`.

1. **Autorização** — `app/core/authz.py`
   - Rota: `ctx: AuthContext = Depends(require("campaigns.view"))` (401 sem token; 403 se não tem a permissão em nenhum escopo). `require(p, global_only=True)` para ações só da equipe RD; `allow_impersonation=False` para ações sensíveis.
   - Recurso: `ctx.ensure("campaigns.manage", org_id=c.org_id, establishment_id=…, city=…)` → 404 fora do escopo; `ctx.can(...)` → bool.
   - Listagem: `.where(ctx.scope_filter("campaigns.view", org_col=Campaign.org_id, establishment_col=…, city_col=…))`; `ctx.org_ids(perm)` (None = GLOBAL).
   - Escopo CITY usa a chave `UF:cidade-normalizada` (`authz.city_key("GO","Goiânia") == "GO:goiania"`); guarde uma coluna `city_key` quando for filtrar por cidade.
   - `ctx.user`, `ctx.user_id`, `ctx.is_super_admin`, `ctx.is_admin_master`, `ctx.impersonation`, `ctx.permissions`. `finance.approve` só vale para Admin Master; permissões financeiras/segurança são negadas durante impersonation.
   - Dispositivos: `authz.register_device_authenticator(fn)` (JWT `typ=device`) e `Depends(get_device_context)`.
   - Catálogo e perfis: `app/core/permissions.py` (`CATALOG`, `ROLE_TEMPLATES`). Código inexistente quebra no import e em `test_permissions_catalog`.
   - Shim legado `app.modules.auth.deps.require_permission("x:y")` exige escopo GLOBAL; ao reescrever, use `require()` + escopo.
2. **Erros** — `app/core/errors.py`: `raise DomainError("CODIGO", "Mensagem pt-BR", status=400, details={})`, `NotFound()`, `Forbidden()`, `Conflict()`, `Locked()`. Envelope do contrato §1 em tudo (inclusive 422).
3. **Banco** — `app/core/database.py`: `get_db` (commit no sucesso, rollback no erro); `independent_session()` (transação separada que persiste mesmo se a request falhar); `worker_session()` para Celery (NullPool por execução). Nunca `echo` de SQL.
4. **Auditoria** — `app/core/audit.py`: `await audit(db, ctx, "campaign.approved", "campaign", c.id, before=…, after=…, reason=…, org_id=c.org_id)` na mesma transação; `audit_independent(...)` para registrar falhas. `audit_logs` é append-only (trigger) e encadeada por hash; chaves sensíveis viram `[REDACTED]`.
5. **DDL extra** — `app/db/ddl.py`: tabelas append-only em `APPEND_ONLY_TABLES` (o harness de testes aplica; a migration deve executar `ddl.append_only_trigger("<tabela>")`).
6. **Configurações** — `app/core/settings_service.py`: `await get_setting(db, "inventory.reservation_hours")`. Defaults: `campaign.approval_mode=MANUAL`, `inventory.reservation_hours=2`, `commission.model=A_POOL`, `commission.pool_bps=500`, `pricing.min_margin_bps=4000`, `player.offline_alert_days=[7,28]`, `cycle.default_internal_s=120`, `cycle.default_external_s=120`, `pix.key_cooldown_hours=12`, `refund.window_days=7`, `proof_of_play.raw_retention_days=90`. Chaves financeiras só mudam com `set_setting(..., approved_by_dual_control=True)` (fluxo de dupla aprovação), senão 409 `SETTING_REQUIRES_DUAL_APPROVAL`. Novas chaves: `register(SettingDef(...))`.
7. **Dinheiro / IDs / tempo** — `app/core/money.py` (int centavos, `apply_bps` com floor, `allocate` com resíduo explícito, `cents_to_reais`/`reais_to_cents` com Decimal; float → TypeError); `app/core/ids.py` (`new_creative_code` RD-XXXXXX, `new_screen_code(uf)` TEL-UF-XXXX, `new_pairing_code` XXXX-XXXX, `generate_unique(gen, exists)` — mantenha UNIQUE no banco); `app/core/timeutils.py` (`utcnow`, `validate_timezone`, `end_of_local_day_utc`, `local_day_bounds_utc`, `isoformat_z`).
8. **Tempo real** — `app/core/events.py`: `await events.publish("campaign.updated", data, org_id=…)` ou `events.publish_sync(...)` em task Celery; `events.subscribe_pattern()`; `events.visible_to(ctx, env)` filtra por escopo; `public_envelope(env)`; tickets `create_ws_ticket`/`consume_ws_ticket` (`POST /api/v1/realtime/ticket`; `/ws/admin` só aceita `?ticket=`).
9. **Registro** — routers em `app/api/v1/router.py` (seções por domínio); models em `app/models/__init__.py` (seções); tasks em `app/workers/celery_app.py` (include + beat por seção; filas em `QUEUES`). Modelo de task: `app/workers/tasks/auth.py` (`run_async` + `worker_session`).
10. **Testes** — PostgreSQL real (banco `rdtest_<uuid>` criado/dropado por execução; `RD_TEST_SCHEMA=alembic` para rodar via migrations), Redis db 15 com prefixo. Rodar: `docker exec -w /app rd-backend python -m pytest -q`. Fixtures: `db`, `client`, `client_factory`, `mail`, `redis`, `clean_state`. Factories (`tests/factories.py`): `make_org`, `make_establishment`, `make_user(db, role="advertiser", scope=("ORGANIZATION", org.id), mfa=False)`, `assign`, `login_as(client, user)`, `auth_headers`, `CSRF`. Marcadores por pasta: unit/integration/concurrency/adversarial/migrations/workers/e2e.
11. **Migrations** — cada revisão nova é encadeada no head atual; triggers via `app/db/ddl.py`; teste dedicado garante zero drift entre models e migrations. Nunca `create_all` fora dos testes.
12. **Bootstrap e Admin Master (AÇÃO 003 — ADR_011)** — fluxo padrão: o serviço one-shot `bootstrap` (compose, após `migrate`) roda `python -m app.cli bootstrap-instance`, que lê `RD_BOOTSTRAP_DUAL_MASTER_APPROVAL` (só na 1ª inicialização; depois o modo vive na trilha selada `instance_approval_mode_history` e o ENV é ignorado com alerta de divergência), `RD_BOOTSTRAP_MASTER_EMAIL`/`_NAME` e `RD_BOOTSTRAP_MASTER_PASSWORD_FILE` (senha só por arquivo/segredo) e cria o Admin Master primário (assento 1) com troca de senha obrigatória — idempotente; erro de configuração ⇒ código 2 sem gravar. **Primeiro acesso** (guard no backend, `app/modules/security/setup.py`): troca de senha → TOTP → senha financeira (403 `PASSWORD_CHANGE_REQUIRED`/`MFA_SETUP_REQUIRED`/`FINANCIAL_PASSWORD_SETUP_REQUIRED` em todo o resto). **2º Master** (modo DUAL): convite pelo painel (`POST /security/masters/invites`, link de uso único só no e-mail do convidado) e ativação atômica com os fatores do próprio convidado. Rota nova fora do guard precisa entrar nas listas explícitas de `tests/unit/test_route_guard_inventory.py`. Ferramentas de **recuperação/automação** (shell no host, auditadas): `bootstrap-masters --seat 1|2` (restrito: só assento vago, nunca transfere, sem `--force-reassign`), `recover-master --seat N --reason "…"` (mesmo titular; zera TOTP/senha financeira; notifica os dois), `security-verify` (selos + titulares; 0/1). `super_admin` não é concedido pela API; `set-password`/`lock-password` recusam titulares de assento. Testes: `tests/factories.py::init_approval_mode` + `adopt_master_seats` (Masters de teste selados). Demais: `sync-permissions`, `seed-dev` (dados de DEMONSTRAÇÃO).
